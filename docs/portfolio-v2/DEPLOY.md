# Публикация портфолио v2

## Текущее решение

Исходники остаются в `Serrybalka/sergey-portfolio`. Новая версия готовится в ветке
`portfolio/pages-v2-20261027`. Стек React, Vite и TypeScript сохранён. Страницы
предварительно рендерятся через официальный Vite SSR API и `react-dom/server`;
на хостинге работают обычные статические HTML, CSS, изображения и JS.

Существующий `.github/workflows/deploy.yml` публикует `main` в Yandex Object
Storage. Он не переключён и не вызывается новым workflow. Не сливайте эту ветку
в `main`, пока не принято решение о переходе: push в `main` запускает прежнюю
production-публикацию. Историческое описание в корневом README не является
подтверждением фактических настроек нового Pages-деплоя.

## Сборка и проверка

```bash
npm ci
npm run build
node scripts/check-pages.mjs
```

Для сборки с префиксом GitHub project Pages:

```bash
PUBLIC_BASE_PATH=/sergey-portfolio/ SITE_URL=https://serrybalka.github.io PUBLIC_INDEXABLE=false npm run build
node scripts/check-pages.mjs
```

В PowerShell эти переменные задаются через `$env:PUBLIC_BASE_PATH`,
`$env:SITE_URL` и `$env:PUBLIC_INDEXABLE` перед той же командой `npm run build`.

- `PUBLIC_BASE_PATH` — `/` локально или `/sergey-portfolio/` на project Pages.
- `SITE_URL` — проверенный origin без пути, query и пароля. Для project Pages
  подготовлено `https://serrybalka.github.io`; это конфигурация, не доказательство
  уже работающей публикации.
- `PUBLIC_INDEXABLE=false` — preview закрыт от индексации метатегом `noindex`.
  Это не контроль доступа: публичные файлы может прочитать посетитель.
- `PUBLIC_INDEXABLE=true` допускается только для готового контента и известного
  HTTPS origin. `/ds/` и 404 остаются `noindex` при любом режиме.
- `JS_GZIP_BUDGET_KB=110` — верхний лабораторный бюджет суммарного клиентского JS.
  Это не показатель LCP/INP/CLS и не доказательство полевой производительности.

`scripts/build-pages.mjs` собирает клиент и временный SSR-модуль в `.prerender/`,
затем создаёт HTML каждого объявленного маршрута, `robots.txt`, `sitemap.xml` и
`.nojekyll`. Технические отчёты находятся в `.prerender/`, вне публикуемого `dist/`.
Публичная сборка не включает исходный SSR-модуль, внутренние брифы, архивы,
материалы NDA или настройки среды агента. Сборка использует только производные
изображения из `public/`; оригиналы хранятся вне него.

Build-плагин в `vite.config.ts` удаляет кейсы `draft` из импортируемого JSON до
создания клиентского и SSR-модулей. Их текст не входит в JS, HTML, навигацию или
sitemap релиза. В dev-сервере исходный JSON остаётся доступен для редактирования,
хотя карточки и маршруты черновиков скрыты. Он должен содержать только безопасный
для просмотра контент: `draft` — редакторский статус, не хранилище секретов.
Всё из `public/` Vite копирует независимо от статуса кейса; закрытые и неготовые
к публикации медиа следует хранить вне `public/`.

Проверка границы черновиков: `node scripts/check-draft-boundary.mjs` временно
добавляет уникальный тестовый кейс, проверяет оба bundle и статические маршруты,
восстанавливает исходный JSON побайтно и повторяет штатную сборку/проверку.

`scripts/check-pages.mjs` проверяет статический текст, H1, метаданные, canonical,
вложенные ссылки и ресурсы с учётом `base`, якоря, alt/размеры изображений,
исключения sitemap, запрещённые файлы/признаки приватных ключей и JS-бюджет.
Результат записывается в `.prerender/check-report.json`. Браузерные, клавиатурные
и визуальные проверки проводятся отдельно и не подменяются этим скриптом.

## GitHub Pages: подготовлено, требуется проверить в аккаунте

`.github/workflows/pages-v2.yml` запускает одинаковые сборку и проверки на push
в новую ветку и в pull request. Из pull request ничего не публикуется. Deploy
зависит от успешной build-задачи и использует её единственный проверенный artifact.
Действующий deploy не отменяется новым push. Дополнительный PAT не нужен:
используется штатный `GITHUB_TOKEN` и OIDC.

Перед первым деплоем владелец или авторизованный агент проверяет:

1. Repository **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. Environment `github-pages` разрешает deployment из
   `portfolio/pages-v2-20261027`; требуемые reviewer approvals выполняет владелец.
3. Actions разрешены в репозитории, официальные `actions/*` разрешены политикой.
4. Публикуется только предназначенный для открытого просмотра контент.

Подготовленный адрес новой версии:
`https://serrybalka.github.io/sergey-portfolio/`. До успешного workflow и проверки
HTTP-ответов он не считается действующим сайтом.

После deployment проверьте главную, `/work/`, каждый кейс, `/about/`, `/ds/` при
прямом входе и обновлении, 404, мобильную версию, контактные ссылки, no-JS fallback
и отсутствие ошибок консоли. Путь `/ds` может перенаправляться на `/ds/`.
Временные обложки имеют видимую маркировку и не являются артефактами проектов.
PDF резюме не публикуется до получения разрешённой финальной версии.

## Собственный домен и REG.RU

В прежнем runbook указан `productsignal.ru`. Это не подтверждение текущего
владения, DNS или решения переключать именно этот домен. Текущая зона,
почтовые записи и существующий хостинг в рамках этого изменения не менялись.

После подтверждения домена и готовности новой версии:

1. Определите авторитетные NS и фактического DNS-провайдера. Сохраните зону и
   таблицу `тип / имя / TTL / было / станет / назначение / откат`.
2. Подтвердите владение через точную TXT-запись, выданную GitHub. Сохраните TXT.
3. Укажите домен в Pages до переключения веб-записей. Сборка собственного домена
   использует `PUBLIC_BASE_PATH=/`, `SITE_URL=https://<подтверждённый-домен>`.
4. Возьмите актуальные A/AAAA/CNAME из документации GitHub; `www` направляется
   CNAME на `serrybalka.github.io`, без протокола и пути. Не создавайте wildcard,
   не очищайте зону и не совмещайте CNAME с A на том же имени.
5. Сохраните MX/SPF/DKIM/DMARC и записи других сервисов. Проверьте NS, A, AAAA,
   CNAME, TXT и CAA у авторитетных серверов и публичных резолверов.
6. Дождитесь сертификата, включите Enforce HTTPS, проверьте HTTP→HTTPS,
   основной адрес и `www`, query/hash и вложенные страницы. DNS и выпуск
   сертификата — разные ожидания; не повторяйте изменения вслепую.

С Actions-публикацией `public/CNAME` не требуется. Не переносите чужое значение
доменного имени из технического примера в конфигурацию. Платный хостинг,
сертификат, NS и услуги старого провайдера автоматически не отключаются.

## Обновление и откат

Контент новой версии и общий UI меняются в исходниках, затем проходят ту же
сборку и проверку. Сначала проверяйте preview. Пока прежний production работает
через `main`, обновления новой версии остаются в выделенной ветке.

Для отката Pages сделайте новый commit в этой же ветке, возвращающий файлы к
последнему проверенному release, и пройдите workflow заново. Сохраняйте SHA
проверенного релиза и URL deployment в PLAN. Не делайте force-push и не
переназначайте основную ветку ради отката. DNS возвращается по сохранённой зоне;
предыдущий хостинг должен оставаться готовым до завершения перехода.

не подключены. GitHub Pages на публичном репозитории не требует отдельного
платного хостинга; условия тарифа аккаунта и стоимость/продление собственного
домена проверяются отдельно. Никакие ключи, пароли или cookies в документацию
или клиентскую сборку не добавляются.

## Предохранитель публикации

Build и проверенный artifact создаются в рабочей ветке. Deploy выполняется только при repository variable `PORTFOLIO_PAGES_ENABLED=true`. До настройки Pages → Source: GitHub Actions и проверки environment `github-pages` оставлять её выключенной. Сейчас UI GitHub в облачном браузере показывает Sign in; настройка Pages не подтверждена. Старый Yandex workflow и доменная зона не менялись. Это ожидание настройки, а не завершённая публикация.
